# Anomaly Path — схемы данных

Дополнение к [GAME_MANIFEST.md](GAME_MANIFEST.md). Здесь только структура данных: файлы, поля, типы, правила.

## 1. Соглашения

- **Формат:** JSON, UTF-8 без BOM. Тексты — не в JSON, а в `.resx` (раздел 2.1).
- **Имена полей:** `camelCase`.
- **Имена файлов:** только латиница, `snake_case` или `camelCase`, расширение `.json`.
- **Имена id:** строчная латиница, цифры и `_`, обязательный префикс категории, шаблон `^[a-z][a-z0-9_]*$`.
- **Префиксы id по видам:**

| Вид | Префикс | Пример |
| --- | --- | --- |
| `Item` | `wpn_`, `ammo_`, `arm_`, `bp_`, `belt_`, `art_`, `itm_` | `wpn_ak74` |
| `Rarity` | `rar_` | `rar_common` |
| `Feature` | `feat_` | `feat_selfloading` |
| `WeaponClass` | `wclass_` | `wclass_rifle` |
| `Skill` | `skill_` | `skill_burst` |
| `StatusEffect` | `status_` | `status_bleed` |
| `DamageType` | `dmg_` | `dmg_bullet` |
| `Actor` (`npc`) | `npc_` | `npc_caravan_boss` |
| `Actor` (`trader`) | `trd_` | `trd_hub_smuggler` |
| `Actor` (`enemy`) | `enemy_` | `enemy_dog` |
| `Event` | `evt_` | `evt_dead_courier` |
| `LootTable` | `loot_` | `loot_car_common` |
| `LocationTemplate` | `loc_` | `loc_road_01` |
| `SpawnEntry` | `spawn_` | `spawn_car_wreck` |
| `Recipe` | `rec_` | `rec_ak74` |
| `Faction` | `fct_` | `fct_caravan` |
| `Quest` | `qst_` | `qst_lost_courier` |
| `Dialog` | `dlg_` | `dlg_caravan_boss` |
| `Unlock` | `unlock_` | `unlock_rifle_shop` |
| `Formula` | `formula_` | `formula_damage_base` |
| `EconomySettings` | `economy` | единственная запись |
| `CombatSettings` | `combat` | единственная запись |
| `GameRules` | `rules` | единственная запись |
| `BalanceSettings` | `balance` | единственная запись |
| `Topology` | `topology` | единственная запись |

- **Ссылки:** всегда строками id, никогда прямыми ссылками на файлы или ассеты.
- **Единицы:** габариты — в клетках; деньги — целые числа; время боя — в ОД; прочность — целые единицы.
- **Числа баланса** живут в данных и помечаются `⏸` в манифесте, а не в коде.
- **Версия схемы:** корневой объект источника и каждого файла содержит `schemaVersion`.
- **Наследование.** В JSON наследования нет, поэтому иерархия выражается общим набором полей плюс полем-дискриминатором `type`. Загрузчик читает общие поля, затем блок наследника. Так `Actor` остаётся одной базовой сущностью, а `Npc`, `Trader`, `Enemy` — её частными случаями.

## 2. Данные и состояние

Разделение обязательно: контент иммутабелен, состояние сохраняется.

| Категория | Что это | Где живёт |
| --- | --- | --- |
| Данные | описания предметов, локаций, рецептов, врагов, событий | JSON: `Assets/Data`, `Mods/<name>/` |
| Тексты | названия, описания, реплики | `.resx`: `Assets/Localization`, `Mods/<name>/Localization` |
| Состояние | инвентарь игрока, сгенерированные локации, прогресс | сейв в `Application.persistentDataPath` |

Правило: **в сейве хранятся только id и изменяемые значения**, никогда — копии описаний. Иначе правка баланса ломает старые сохранения.

Следствие: любое поле, которое меняется в игре (убитый враг, снятый лут, износ, флаг события), в данных отсутствует, а в сейве присутствует.

### 2.1. Локализация: `.resx`

Тексты не дублируются в JSON. В данных лежит **ключ**, текст — в ресурсах.

**Файлы:**

```
Assets/Localization/Resources/Strings.ru.resx
Assets/Localization/Resources/Strings.en.resx
Mods/<name>/Localization/Strings.ru.resx
Mods/<name>/Localization/Strings.en.resx
```

**Формат ключа:** `<вид>.<id>.<поле>`, латиница в нижнем регистре, точки как разделители.

| Сущность | Поле | Пример ключа |
| --- | --- | --- |
| `Item` | `nameKey` | `item.wpn_ak74.name` |
| `Item` | `descriptionKey` | `item.wpn_ak74.desc` |
| `LocationTemplate` | `titleKey` | `loc.loc_road_01.title` |
| `Event` | `titleKey`, `textKey` | `event.evt_dead_courier.text` |
| `Quest` | `titleKey`, `descriptionKey` | `quest.qst_lost_courier.title` |
| `Actor` | `nameKey` | `npc.npc_caravan_boss.name` |
| `Skill` | `nameKey`, `descriptionKey` | `skill.skill_burst.name` |
| `DamageType` | `nameKey` | `damage.dmg_bullet.name` |
| `Rarity` | `nameKey` | `rarity.rar_rare.name` |
| `Feature` | `nameKey`, `descriptionKey` | `feature.feat_selfloading.name` |
| `Dialog` | узлы и варианты | `dlg.dlg_caravan_boss.hello` |
| Интерфейс | — | `ui.inventory.title`, `ui.button.leave` |

Префикс ключа — **вид в единственном числе** (`item`, `loc`, `event`, `quest`, `npc`, `skill`, `damage`, `rarity`, `feature`, `dlg`), даже если `kind` во множественном. Валидатор сверяет префикс с видом сущности.

**Правила:**

- В данных **нет** полей `name`, `description`, `title`, `text`. Только ключи.
- Языки: `ru` — основной, `en` — второй. Русский файл — эталон: ключ, которого нет в `ru`, ошибка валидации.
- Загрузчик: собственный парсер `.resx` (XML) в словарь. Стандартный `ResourceManager` и сателлитные сборки **не используются**: Unity не собирает их для игровых данных, а моды не могут добавлять свои сборки.
- Порядок разрешения: текущий язык → `en` → сам ключ. Отсутствие перевода не ломает игру, но валидатор помечает расхождение наборов ключей между `ru` и `en`.
- ❓ Формат `resx` поддерживает `<comment>` и метаданные — используем только `data`/`value`; остальное игнорируется.

- **Одна сущность — один файл.** Имя файла совпадает с `id` сущности (`loc_road_01.json` содержит `"id": "loc_road_01"`). Так файл можно найти по id и править поштучно.
- **Коллекция — тоже файл.** `col_weapons.json` перечисляет ссылки на все оружия проекта; загрузчик подхватывает коллекцию и сама подтягивает перечисленные файлы. В каталоге указываются коллекции, а не сотни отдельных файлов (раздел 3.3.1).
- Папка соответствует виду (`items/`, `locations/`), но решает `catalog.json`: он перечисляет файлы верхнего уровня — коллекции, синглтоны и, при желании, отдельные сущности.
- Файлы `_base/` — **абстрактные шаблоны**: не сущности, не регистрируются, существуют только чтобы от них наследовались (раздел 3.4).
- **Мод — это данные и ассеты, кода в нём нет.** Новые скиллы, эффекты и формулы выражаются данными, а не C#; загрузчика сборок в игре нет. Моды живут в `Mods/<name>/` со своей структурой и манифестом `mod.json` (раздел 3.8).
- `Mods/` читается из `Application.persistentDataPath/Mods/<name>/`; базовый контент в сборке — из `StreamingAssets/Data` (копия `Assets/Data`).
- ❓ В редакторе читать прямо из `Assets/Data`, без копирования в `StreamingAssets`. Подтвердить при написании загрузчика.

### 3.2. `catalog.json`

```json
{
  "schemaVersion": 1,
  "id": "core",
  "name": "Базовый контент",
  "version": "0.1.0",
  "priority": 0,
  "files": [
    "topology.json",
    "balance.json",
    "items/col_weapons.json",
    "items/col_ammo.json",
    "locations/col_locations.json"
  ]
}
```

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `schemaVersion` | int | да | версия схемы, которую понимает содержимое |
| `id` | string | да | id источника: `core` для базового, имя мода для мода |
| `name` | string | нет | отображаемое имя мода (не переводится) |
| `version` | string | нет | версия мода, semver |
| `priority` | int | нет | порядок наложения, по умолчанию 0; больше — позже |
| `files` | string[] | да | пути относительно корня источника, **порядок значим** |
| `includes` | string[]? | нет | другие каталоги того же источника, подключаемые целиком (удобно для модов: `catalogs/weapons.json`) |

Файлы перечисляются явно: загрузчик не сканирует каталоги, поэтому порядок детерминирован. Поле `includes` позволяет разбить каталог на части, не теряя порядка.

### 3.3. Файл сущности

Один файл — одна сущность.

```json
{
  "schemaVersion": 1,
  "kind": "items",
  "id": "wpn_ak74",
  "extends": "_base/weapon_rifle.json",
  "include": ["_base/priced_standard.json"],
  "nameKey": "item.wpn_ak74.name",
  "category": "weapon",
  "footprint": [2, 3],
  "maxStack": 1,
  "weapon": { "damage": 12, "accuracy": 0.55, "magazine": 30 }
}
```

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `schemaVersion` | int | да | версия схемы файла |
| `kind` | enum | да | вид сущности; у абстрактного шаблона тоже обязателен |
| `id` | string | да* | id сущности; у абстрактного файла можно опустить |
| `abstract` | bool | нет | `true` — шаблон, не сущность: не регистрируется, нужен только для наследования |
| `extends` | string | нет | путь к родительскому файлу, **один**; вид должен совпадать |
| `include` | string[] | нет | пути к файлам, которые подмешиваются целиком (миксины) |
| … | — | — | остальные поля вида (разделы 4–17) |

`kind` перечисляет всё, что описано в схемах: `items`, `rarities`, `features`, `weaponClasses`, `skills`, `statuses`, `damageTypes`, `actors`, `events`, `lootTables`, `locations`, `topology`, `spawns`, `recipes`, `factions`, `quests`, `dialogs`, `unlocks`, `formulas`, `balance`, `economy`, `combat`, `rules`.

Файлов в проекте три вида, различаются полем-признаком:

| Вид файла | Признак | Что содержит |
| --- | --- | --- |
| **Сущность** | `kind` + `id` | один объект: оружие, локация, NPC |
| **Коллекция** | `"collection": true` | список ссылок на файлы сущностей одного вида |
| **Синглтон** | своя запись (`id`: `balance`, `topology`…) | одна глобальная настройка, перечисляется в каталоге напрямую |

### 3.3.1. Файл-коллекция

Пакет сущностей одного вида: перечисляет, что есть в проекте, и загружается вместо сотни отдельных строк в каталоге.

```json
{
  "schemaVersion": 1,
  "kind": "items",
  "collection": true,
  "id": "col_weapons",
  "entries": [
    "items/wpn_ak74.json",
    "items/wpn_akm.json",
    "items/wpn_mosin.json"
  ]
}
```

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `schemaVersion` | int | да | версия схемы |
| `kind` | enum | да | вид сущностей; все `entries` обязаны быть того же вида |
| `collection` | bool | да | всегда `true` — отличает коллекцию от сущности |
| `id` | string | нет | имя коллекции для логов и отладки: `col_weapons` |
| `entries` | string[] | да | пути к файлам сущностей, порядок значим |
| `include` | string[]? | нет | другие коллекции того же вида, подключаемые целиком |

Правила:

- Загрузчик встречает `collection: true`, читает `entries`, загружает каждый файл как сущность и регистрирует по её `id`. В каталоге достаточно указать коллекцию.
- `entries` — **ссылки на файлы**, а не копии сущностей: правка оружия остаётся в одном файле.
- Один и тот же файл в двух коллекциях — **ошибка валидации** (дубль `id`).
- Коллекция может вкладывать коллекции через `include`; циклы запрещены.
- Порядок `entries` задаёт порядок регистрации — важно для модов и для детерминизма.
- Коллекция не может быть целью ссылки: ссылаются на сущности, а не на список.
- Сущность, не попавшая ни в одну коллекцию и не указанная в каталоге, считается недостижимой: предупреждение валидатора.

### 3.4. Наследование и включения

**Два разных механизма, не путать:**

| Механизм | Что делает | Ограничения |
| --- | --- | --- |
| `extends` | **наследование**: файл-ребёнок того же вида, поля родителя глубоко сливаются, ребёнок перекрывает | один родитель, цепочка допустима, циклы запрещены, `kind` у всей цепочки одинаковый |
| `include` | **подмешивание**: любые файлы, независимо от вида; поля сливаются так же | порядок значим, следующий перекрывает предыдущий, циклы запрещены |

Пример: `weapon_rifle.json` в `_base/` описывает общее для всех винтовок, `wpn_ak74.json` наследует его через `extends` и перекрывает числа. Общий блок цены вынесен в `_base/priced_standard.json` и подмешивается через `include` — цены не в иерархии оружия, но нужны многим видам.

**Слияние полей:**

- объекты сливаются **глубоко**, по ключам;
- массивы **заменяются целиком**, а не сливаются поэлементно;
- скаляры перекрываются;
- `null` удаляет поле из результата (позволяет «стереть» унаследованное);
- `id`, `kind`, `schemaVersion` не наследуются — берутся у конечного файла.

**Порядок применения:** сначала цепочка `extends` (от корня вниз), затем `include` в указанном порядке, затем поля самого файла.

### 3.5. Порядок загрузки и наложение источников

1. `core` — всегда первым.
2. Моды — по возрастанию `priority`, при равенстве — по имени папки.
3. Файлы внутри источника — в порядке массива `files` (+ `includes`).
4. Коллекция разворачивается на месте: её `entries` загружаются в указанном порядке, затем `include`-коллекции.

| Ситуация | Результат |
| --- | --- |
| одинаковый `id` дважды в одном источнике | **ошибка валидации**, источник не загружается |
| один файл сущности в двух коллекциях | **ошибка валидации** (дубль `id`) |
| `entries` коллекции содержат сущность другого `kind` | **ошибка валидации** |
| цикл между коллекциями (`include`) | **ошибка валидации** |
| сущность не попала ни в одну коллекцию и не указана в каталоге | предупреждение: недостижимый файл |
| `id` сущности мода совпадает с `id` из базы | **полная замена сущности** модом (не слияние), предупреждение в лог |
| `id` коллекции мода совпадает с базовой | **замена списка `entries`** целиком |
| два мода перекрывают один `id` | перекрывает мод с большим `priority`, предупреждение в лог |
| `extends`/`include` ссылается на несуществующий файл | **ошибка валидации** источника |
| цикл в `extends`/`include` | **ошибка валидации** источника |
| `extends` между разными `kind` | **ошибка валидации** источника |
| `abstract`-файл используется как сущность (попал в реестр) | ошибка валидации |
| одинаковый ключ локализации у мода и базы | мод перекрывает значение |
| мод ссылается на несуществующий `id` | мод не загружается целиком |
| `removals` удаляет `id`, на который ссылается неудалённый контент | **ошибка загрузки** |
| `schemaVersion` мода выше поддерживаемой | мод отключается с сообщением |

Мод может не только заменить сущность целиком, но и **наследоваться от неё**: файл мода с новым `id` и `"extends": "items/wpn_ak74.json"` даёт вариант предмета, не копируя поля.

Отключение мода — переименование или удаление его папки. Отдельного реестра модов нет.

### 3.6. Классы и файлы: соответствие

**Код описывает тип, файл — конкретный объект.** Правило действует для всех сущностей без исключений.

| Уровень | Где | Что содержит |
| --- | --- | --- |
| Абстрактный класс | C# | общие поля и правила вида: `EntityTemplate`, `ItemTemplate`, `ActorTemplate`… |
| Класс вида | C# | поля конкретного вида: `WeaponTemplate : ItemTemplate`, `NpcTemplate : ActorTemplate` |
| Конкретный объект | JSON-файл | значения полей: `wpn_ak74.json`, `npc_caravan_boss.json` |
| Экземпляр в игре | сейв | изменяемое состояние, ссылка на `id` |

Правила:

- **Один класс на вид, а не на объект.** Класса `Ak74` в коде быть не должно — только `WeaponTemplate` и файл с числами.
- Наследование классов в C# повторяет наследование данных: `Actor` → `Npc` → `Trader`; `Item` → `Weapon`/`Armor`/…; `Effect` — единый тип с `type`, а не класс на каждый эффект.
- **Поведение — отдельно от описания.** Класс хранит данные и умеет их валидировать; механики (укладка, бой, крафт, взаимодействия предметов) живут в сервисах `AnomalyPath.Core`, а не в классах-описаниях. Какие предметы с чем взаимодействуют — будет решаться механиками и функциями поверх данных (раздел 4.13 ❓).
- Загрузчик читает файл → если это коллекция, разворачивает её → выбирает класс по `kind`/`type`/`category` → заполняет поля → валидирует → кладёт в реестр по `id`.
- Коллекция классу не соответствует: это список файлов, а не сущность. Класс есть только у сущности.
- Один файл — одна сущность; объединять несколько записей в файл нельзя. Несколько сущностей перечисляются коллекцией (раздел 3.3.1).

### 3.7. Разрешение ссылок

- Ссылки разрешаются **после** загрузки всех источников.
- Ссылка проверяется по ожидаемому виду: `lootTable` → `LootTable`, `itemId` → `Item`, `classId` → `WeaponClass`, `damageTypeId` → `DamageType`, `actorId` → `Actor` (с проверкой допустимого `type`, см. раздел 19).
- Неразрешённая ссылка — ошибка загрузки источника, а не «пустое поле».

### 3.8. Моды

Мод — отдельный источник со своей структурой и манифестом. Он **подключается последним и перекрывает загруженное раньше**.

**Структура:**

```
Mods/<modName>/
  mod.json                  # манифест: что подключаем и что перекрываем
  Data/                     # сущности и коллекции мода
    items/wpn_akm_tuned.json
    items/col_weapons.json  # новая версия базовой коллекции
  Localization/
    Strings.ru.resx
    Strings.en.resx
  Assets/                   # спрайты, звуки, шрифты
```

**`mod.json`:**

```json
{
  "schemaVersion": 1,
  "id": "hardcore_loot",
  "name": "Хардкорный лут",
  "version": "1.0.0",
  "author": "VlomInc",
  "priority": 10,
  "includes": ["Data/items/col_weapons.json", "Data/items/col_ammo.json"],
  "entities": ["Data/items/wpn_akm_tuned.json"],
  "overrides": {
    "collections": ["Data/items/col_weapons.json"],
    "entities": ["Data/items/wpn_ak74.json"]
  },
  "removals": ["itm_broken_trash"]
}
```

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `schemaVersion` | int | да | версия схемы, которую понимает мод |
| `id` | string | да | id мода, уникален среди модов |
| `name` | string | да | отображаемое имя |
| `version` | string | нет | semver |
| `author` | string | нет | автор |
| `priority` | int | да | порядок загрузки; больше — позже и перекрывает раньше загруженных |
| `includes` | string[] | нет | коллекции мода, которые добавляют сущности к базе |
| `entities` | string[] | нет | отдельные сущности мода (новые `id`) |
| `overrides` | object | нет | `{ collections: [...], entities: [...] }` — файлы, которые заменяют одноимённые записи базы |
| `removals` | string[] | нет | `id` сущностей, которые мод убирает ❓ |

**Правила:**

- Мод **не может добавлять код** — только данные и ассеты.
- **Перекрытие по `id`:** сущность мода с тем же `id`, что у базы, заменяет её целиком (не слияние). Коллекция мода с тем же `id`, что у базовой, заменяет её список `entries` целиком.
- Мод может **наследоваться** от базовой сущности (`extends`) и делать вариант с новым `id` — это не перекрытие.
- Мод видит только источники с меньшим `priority` (база и ранее загруженные моды), но не последующие.
- `removals` убирает сущности базы; ссылки на удалённые `id` из неудалённого контента — **ошибка загрузки**.
- Порядок: `core` → моды по возрастанию `priority`, при равенстве — по имени папки → внутри мода сначала `includes` и `entities`, затем `overrides`.
- Два мода с одинаковым `id` сущности — перекрывает поздний, в лог пишется предупреждение.
- Мод без `mod.json` или с несовместимым `schemaVersion` **не загружается целиком** и не ломает остальные.
- Отключение — переименование или удаление папки; реестра модов нет.

## 4. Item

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `id` | string | да | уникальный идентификатор |
| `nameKey` | string | да | ключ локализации названия |
| `descriptionKey` | string | нет | ключ локализации описания |
| `category` | enum | да | `weapon`, `ammo`, `armor`, `helmet`, `backpack`, `belt`, `artifact`, `consumable`, `trophy`, `material`, `quest` |
| `footprint` | [int, int] | да | габариты в клетках: `[w, h]`, каждое ≥ 1 |
| `rotatable` | bool | нет | по умолчанию `true` |
| `maxStack` | int | да | 1 = не стакается |
| `price` | object | нет | цена и правило её изменения (раздел 4.9) |
| `equipSlots` | string[] | нет | слоты, куда предмет можно надеть; по умолчанию выводится из категории (раздел 10) |
| `extraRows` | int | нет | у `backpack`: сколько строк добавляет сетке |
| `artifactSlots` | int | нет | у `armor` и `belt`: сколько артефактов даёт предмет |
| `artifactType` | enum | у артефактов | `fire`, `electric`, `chemical`, `gravity`; обязателен для `category = artifact` |
| `protection` | object | нет | у `armor` и `helmet`: защита по типам урона: `dmg_bullet`, `dmg_electric`, `dmg_chemical`, `dmg_fire`, `dmg_rupture` |
| `durabilityMax` | int | нет | у `armor` и `helmet`: максимум прочности, задаётся в файле предмета |
| `material` | enum | нет | у `armor` и `helmet`: `light`, `medium`, `heavy`; по умолчанию `medium` |
| `durabilityFactor` | number | нет | коэффициент износа материала (`light` 1.0, `medium` 1.2, `heavy` 1.5, `exoskeleton` 1.7) |
| `quality` | number | нет | качество предмета, по умолчанию `1` |
| `icon` | string | да | путь к спрайту относительно корня иконок |
| `tier` | int | да | **тир предмета**: ступень силы; у оружия и брони от него растут базовые характеристики |
| `tags` | string[] | нет | свободные метки для фильтров и правил |
| `sellable` | bool | нет | по умолчанию `true`; `false` для сюжетных |
| `droppable` | bool | нет | по умолчанию `true`; `false` для сюжетных |

**Вес отсутствует.** Ограничение инвентаря — только клетки. Поля `weight` нет и не будет; модификаторы веса, перегруз и связанные правила не вводятся.

Правило: **категория и блок совпадают**. `category = "weapon"` требует блок `weapon`; у `material` блока нет.

**Тир и редкость — разные вещи.** `tier` — свойство шаблона предмета (автор задаёт, насколько он силён). `rarity` — свойство **экземпляра**: один и тот же `wpn_ak74` может выпасть обычным, редким и так далее (шесть ступеней — раздел 4.11). Редкость **раскатывает каждую характеристику по своему диапазону** и добавляет скиллы и особенности. Базовые числа в данных — это «обычный» вариант; раскатка происходит один раз при создании экземпляра и записывается в него.

**Редкость есть только у оружия, брони и артефактов.** У расходников, патронов, трофеев, материалов и квестовых предметов редкости нет вообще.

### 4.1. `ammo`

| Поле | Тип | Смысл |
| --- | --- | --- |
| `caliber` | string | `"7.62x39"`; для группировки и правил оружия |
| `damageModifier` | number | множитель к урону оружия |
| `penetration` | number | добавка к бронебойности оружия |

Разные типы одного калибра — **разные `itemId`**. `ammo_762x39_fmj` и `ammo_762x39_ap` не смешиваются в стопку автоматически.

### 4.2. `weapon`

| Поле | Тип | Смысл |
| --- | --- | --- |
| `classId` | string | ссылка на `WeaponClass` |
| `damage` | number | базовый урон |
| `damageTypeId` | string | тип урона; по умолчанию `dmg_bullet` |
| `armorPenetration` | number | бронебойность: насколько снижается защита цели |
| `accuracyCoefficient` | number | коэффициент точности: пистолет 0.8, автомат 1.0, снайперка 1.5 |
| `ignoresDistance` | bool | не штрафовать за дальнюю дистанцию (снайперские винтовки); по умолчанию `false` |
| `magazine` | int | патронов в магазине |
| `ammoCaliber` | string | какой калибр принимает |
| `reloadTime` | number | в ОД |
| `skills` | string[] | id скиллов, доступных на этом оружии (подмножество скиллов класса) |
| `durabilityMax` | int | **обязательно**; максимум прочности ⏸ |
| `durabilityPerShot` | number | сколько прочности тратит один выстрел ⏸ |

### 4.3. `armor`

| Поле | Тип | Смысл |
| --- | --- | --- |
| `protection` | object | `{ [damageTypeId]: number }` — сколько урона типа поглощается |
| `artifactSlots` | int | сколько артефактов можно надеть в этом костюме |
| `covers` | string[] | какие зоны закрывает ❓ нужно ли |
| `modifiers` | Modifier[] | штрафы и бонусы (раздел 11.4) |
| `durabilityMax` | int | **обязательно**; максимум прочности |
| `material` | enum | `light`, `medium`, `heavy`; задаёт множитель `durabilityFactor` |
| `durabilityFactor` | number | коэффициент износа материала (`light` 1.0, `medium` 1.2, `heavy` 1.5, `exoskeleton` 1.7) |
| `quality` | number | качество, по умолчанию `1` |

Правило износа: оружие теряет прочность за выстрел, броня — за попадание по владельцу. Износ брони и шлема: `ceil(урон / (durabilityFactor × quality × 10))`, минимум 1 за попадание: потеря пропорциональна урону и уменьшается с ростом прочности материала и качества. Износ списывается со стопки целиком (раздел 6) и меняет её ключ, то есть при разной прочности вещи автоматически расходятся по стопкам.

`protection` — набор ключей по типам урона. Допустимые ключи берутся из загруженных `DamageType` (`damage/*.json`): `dmg_bullet`, `dmg_electric`, `dmg_chemical`, `dmg_fire`, `dmg_rupture`. Защита от пулевого урона (`dmg_bullet`) — это **пулестойкость**. Формула одна для всех типов: `GetProtection(equipment, damageType)` суммирует значения шлема и брони; используется **только при расчёте урона по здоровью персонажа**. Износ (потеря прочности) считается отдельной формулой и от `protection` не зависит.

### 4.9. `price`

Цена бывает фиксированной или зависящей от репутации. Режим задаётся полем `mode`.

Фиксированная:

```json
{ "mode": "fixed", "buy": 120, "sell": 60 }
```

| Поле | Тип | Смысл |
| --- | --- | --- |
| `mode` | enum | `fixed` или `reputation` |
| `buy` | int | цена покупки игроком |
| `sell` | int | цена продажи игроком |

С репутацией:

```json
{ "mode": "reputation", "base": 120, "factionId": "fct_caravan", "sellRatio": 0.5 }
```

| Поле | Тип | Смысл |
| --- | --- | --- |
| `base` | int | базовая цена до множителей |
| `factionId` | string | чья репутация влияет |
| `sellRatio` | number | доля от цены покупки при продаже; по умолчанию из `EconomySettings` |

Итоговая цена считается как `base × множитель репутации × множитель торговца`, затем округляется по `EconomySettings.rounding` и не опускается ниже `minPrice`. Конкретные множители — данные фракции (`priceTiers`) и торговца, не код.

### 4.10. `EconomySettings` (вид `economy`)

Единственная запись, глобальные правила экономики.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | всегда `economy` |
| `rounding` | enum | `round`, `floor`, `ceil` |
| `minPrice` | int | нижняя граница цены |
| `currency` | string | ключ валюты, одна на игру: `currency.rub` (рубли) |
| `defaultSellRatio` | number | доля продажи по умолчанию |

### 4.11. `Rarity` (вид `rarities`)

Редкость — свойство экземпляра. Шесть ступеней, заданных в данных:

| id | Название | `order` |
| --- | --- | --- |
| `rar_common` | обычная | 0 |
| `rar_rare` | редкая | 1 |
| `rar_special` | особая | 2 |
| `rar_epic` | эпическая | 3 |
| `rar_legendary` | легендарная | 4 |
| `rar_unique` | уникальная | 5 |

Поля записи:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | `rar_rare` |
| `nameKey` | string | «Редкая» |
| `order` | int | 0..5, ступень |
| `statRolls` | object | диапазоны розыгрыша характеристик: `{ [stat]: [min, max] }` — множители к базовому значению |
| `skillRolls` | [int, int]? | сколько доп. скиллов выпадает; `null` — ни одного |
| `skillPools` | `{ [weaponClassId]: string[] }` | **свои пулы доп. скиллов по классам оружия**: `{ "wclass_rifle": ["skill_aimed", "skill_burst"], "wclass_pistol": ["skill_double"] }` |
| `featureRolls` | [int, int]? | сколько особенностей выпадает |
| `featurePool` | string[] | из каких `feat_` выбирать |
| `priceFactor` | number | множитель цены |
| `dropWeight` | number | базовый вес при выпадении |

Ключи `statRolls`:

| Ключ | Что раскатывается |
| --- | --- |
| `damage` | урон оружия |
| `accuracy` | точность оружия |
| `durabilityMax` | максимум прочности оружия и брони |
| `protection` | каждая защита по типу урона (множитель применяется ко всем ключам `protection`) |
| `modifierValue` | величина каждого модификатора артефакта или особенности |

Правила:

- **Редкость есть у оружия, брони и артефактов.** У расходников, патронов, трофеев, материалов, квестовых предметов, **рюкзаков и поясов** редкости нет вообще — ни поля, ни цены по редкости.
- **Все характеристики раскатываются индивидуально.** При создании экземпляра для каждого ключа из `statRolls` берётся случайное значение в диапазоне, умножается на базовое из `Item`, округляется по `BalanceSettings.statRounding` и записывается в `ItemInstance.stats`. Два «редких» автомата будут отличаться уроном и прочностью.
- Розыгрыш детерминирован: используется seed экземпляра (из seed локации или сейва), поэтому одинаковый seed даёт одинаковую вещь — это проверяемо тестами.
- Базовые числа в `Item` — «обычный» вариант; у `rar_common` диапазоны обычно `[1.0, 1.0]`, у высших ступеней — шире и выше.
- Выпавшие скиллы и особенности записываются в экземпляр (`ItemInstance.skills`, `ItemInstance.features`) и не меняются до продажи или поломки.
- Редкость не влияет на `footprint`, `maxStack` и категорию.
- **Скиллы от редкости — только из класса оружия.** У каждой редкости свой пул на класс (`skillPools[wclass_*]`), поэтому автомат получает лишь те скиллы, что объявлены у класса. Пул редкости не может добавить чужой класс-скилл — валидатор это проверяет.
- `featurePool` относится к оружию, брони и артефактам; валидатор проверяет, что особенность применима к категории экземпляра.
- Раскатанные значения пишутся в `stats` с ключом по источнику: `<featureId>.<stat>` для особенности и `modifier.<stat>` для артефакта. Так две особенности на один стат не схлопываются.

### 4.12. `Feature` (вид `features`)

Особенность предмета — пассивное свойство, которое появляется от редкости.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | `feat_selfloading` |
| `nameKey` | string | «Самозарядка» |
| `descriptionKey` | string | 1–2 предложения |
| `modifiers` | Modifier[] | пассивные изменения (раздел 11.4) |
| `effects` | Effect[]? | разовые или условные эффекты, если нужны |
| `tags` | string[] | метки для правил и фильтров |
| `categories` | string[] | к каким категориям применима: `weapon`, `armor`, `artifact` |

Правила:

- Особенности бывают только у оружия и брони; у прочих категорий поле не используется.
- Набор особенностей ограничен редкостью: `Rarity.featurePool`.
- Одна и та же особенность не выпадает дважды у одного экземпляра.
- Значения внутри особенности тоже могут раскатываться (`modifierValue` в `statRolls`), результат пишется в `ItemInstance.stats`.

### 4.13. Взаимодействия предметов

❓ **Не описано, обсуждается.** Предметы будут взаимодействовать через **механики и функции**, а не через классы на каждый предмет: код описывает правило, данные — с чем и как оно применяется.

Пока зафиксированы только рамки, чтобы механику не пришлось встраивать в классы:

- взаимодействие описывается данными (участники, условия, эффект) и выполняется сервисом в `AnomalyPath.Core`;
- участники задаются `itemId`, `tags` и категориями, а не отдельными классами предметов;
- новый вид взаимодействия (например «патрон + магазин = снаряжённый магазин») — новая механика в коде плюс данные, а не новый класс предмета;
- конкретный синтаксис появится, когда дойдём до крафта и использования предметов.

## 5. Габариты и поворот

- `footprint = [w, h]` — габариты в клетках в «нормальной» ориентации.
- Если `rotatable = true`, допустимы обе ориентации: `[w, h]` и `[h, w]`.
- Предмет обязан целиком помещаться внутри сетки: `x + w ≤ width` и `y + h ≤ rows`.
- Предмет не может пересекаться с другими занятыми клетками.
- Клетки адресуются целыми числами от 0; начало координат — левый верхний угол сетки.

## 6. Стеки

- Стопка — один экземпляр предмета с `count > 1`.
- **Ключ стопки — `(itemId, durability, variantKey)`**: стакаются предметы одного `itemId` с одинаковой прочностью **и одинаковым вариантом** (редкость, скиллы, особенности). У предметов без прочности и без редкости ключ сводится к `itemId`.
- **Вариант `variantKey`** — строка-отпечаток: `rarity` + отсортированные `skills` и `features` + `stats`. У обычного предмета без дополнений и раскатки — пустая строка. Считать его один раз при создании экземпляра, а не на каждом сравнении.
- Разная редкость, разные особенности или **разные раскатанные характеристики** — **разные стопки**, даже если `itemId` совпадает.
- Стопка возможна, только если `maxStack > 1`.
- **Прочность принадлежит стопке целиком**, а не отдельным единицам: внутри стопки у всех вещей одинаковый износ.
- Граничные состояния стакаются между собой: `durability = 0` — со сломанными, `durability = durabilityMax` — с новыми. Частичный износ даёт отдельные стопки по каждому значению прочности.
- Стопка занимает `footprint` (обычно `[1,1]` у патронов), а не одну клетку на единицу.
- Частичное добавление: если в стопке осталось место меньше, чем переносится, остаток уходит в новую стопку **с той же прочностью**.
- Слияние стопок не усредняет прочность: сливаются только стопки с равной `durability`, иначе рядом появляется новая стопка.

## 7. GridContainer

| Поле | Тип | Смысл |
| --- | --- | --- |
| `width` | int | фиксированная ширина: рабочее 8, альтернатива 6 |
| `rows` | int | число строк; определяется рюкзаком и прокачкой |
| `items` | ItemInstance[] | размещённые и переполненные предметы |

`rows` вычисляется: `GameRules.baseRows + backpack.extraRows`; в сейве не хранится, чтобы не расходиться с правилами.

## 8. ItemInstance (состояние)

| Поле | Тип | Смысл |
| --- | --- | --- |
| `instanceId` | string | уникальный id экземпляра (GUID), не равен `itemId` |
| `itemId` | string | ссылка на `Item` |
| `count` | int | ≥ 1 |
| `x`, `y` | int | позиция левого верхнего угла; отсутствует при переполнении |
| `rotated` | bool | повёрнут ли на 90° |
| `state` | enum | `placed` или `overflow` |
| `durabilityMax` | int | максимум прочности, раскатанный редкостью; для предметов без прочности отсутствует |
| `durability` | int | текущая прочность; обязательна, если у предмета есть `durabilityMax`; относится ко всей стопке |
| `rarity` | string | `rar_` id редкости; обязательна для оружия, брони и артефактов |
| `stats` | object | раскатанные характеристики: `{ "damage": 14, "accuracy": 0.58, "protection.dmg_bullet": 4, "feat_selfloading.damage": 1, "modifier.healthMax": 12 }` |
| `skills` | string[] | доп. скиллы, выпавшие от редкости; складываются со скиллами предмета |
| `features` | string[] | особенности (`feat_` id), выпавшие от редкости |
| `variantKey` | string | отпечаток варианта: `rarity` + `skills` + `features` + `stats`; часть ключа стопки |
| `data` | object | свободные изменяемые данные экземпляра (например, `{"ammoLoaded": 12}`) |

Правила:

- Новая вещь получает `durability = item.durabilityMax`.
- `durability = 0` — предмет сломан: использовать по назначению нельзя, пока не отремонтирован. Ремонт — `Recipe` с `kind = "repair"`, полевой набор или станок (раздел 16).
- Прочность — свойство стопки, а не единицы: `ItemInstance` с `count = 5` и `durability = 40` — это пять одинаково изношенных вещей.
- Поэтому при добавлении в инвентарь ищется стопка с тем же `itemId`, тем же `durability` и тем же `variantKey`; при равных значениях вещи сливаются, при разных — создаётся отдельная стопка.
- Ремонт одной вещи из стопки выделяет её в новую стопку с новой прочностью: ключ стопки изменился.
- `rarity`, `skills`, `features` и `stats` задаются при создании экземпляра и не меняются; пересчитывать их при загрузке сейва нельзя — иначе старые сохранения «переедут» на новые правила.
- Боевые и экономические расчёты берут значения из `stats`, а не из `Item`: база нужна только чтобы понять, от чего раскатывали.
- Для предметов без редкости (`stats` отсутствует) расчёт идёт по базовым числам `Item`.
- Если редкость или особенность исчезли из данных, экземпляр остаётся с прежним `variantKey`, а в лог пишется предупреждение: вещь не ломается.
- `data` — не свалка: всё, что читает логика, получает поле в схеме.

## 9. Переполнение

Состояние `overflow` возникает, когда после уменьшения `rows` предмет перестаёт помещаться.

- У `overflow`-экземпляра нет `x` и `y`.
- Разрешено только действие «переложить»: в свободную область сетки, на склад, на землю.
- Запрещены: экипировка, использование, продажа, крафт-ингредиент, выброс как обычное действие.
- Предмет не блокирует остальной инвентарь и не мешает играть.
- **При увеличении `rows` переполнение раскладывается автоматически** по свободным клеткам. Порядок детерминирован: сначала предметы в порядке появления, для каждого — первая свободная позиция сверху вниз и слева направо, с учётом `rotatable` (сначала «как есть», затем поворот). Если места нет, предмет остаётся в переполнении.
- Авторазмещение не трогает уже размещённые предметы и не переставляет их.

## 10. Снаряжение и слоты

| Слот | Что принимает | Количество |
| --- | --- | --- |
| `main` | любое оружие | 1 |
| `secondary` | оружие, у которого в `equipSlots` есть `secondary` (холодное, пистолеты, ПП, короткие автоматы, короткие дробовики) | 1 |
| `helmet` | `helmet` | 1 |
| `armor` | `armor` | 1 |
| `backpack` | `backpack` | 1 |
| `belt` | `belt` (пояс артефактов) | 1 |
| `quick_1` … `quick_M` | оружие или расходник | M |

**Слоты задаются данными, а не кодом.** У предмета есть `equipSlots`; если поле не указано, оно выводится из категории: `weapon` → `main`, `helmet` → `helmet`, `armor` → `armor`, `backpack` → `backpack`, `belt` → `belt`, `consumable` → `quick`. Оружие, которое можно носить во втором слоте, просто перечисляет оба слота: `"equipSlots": ["main", "secondary"]`. Мод может добавить новое оружие без правки кода.

**`M` — число быстрых слотов** задаётся записью вида `equipment` (файл `equipment.json`):

| Поле | Тип | Смысл |
| --- | --- | --- |
| `quickSlots` | int | число слотов быстрого доступа; по умолчанию 4 |

| Поле | Тип | Смысл |
| --- | --- | --- |
| `equipment` | object | `{ "main": instanceId?, "secondary": instanceId?, "helmet": instanceId?, "armor": instanceId?, "backpack": instanceId?, "belt": instanceId?, "quick": instanceId[] }` |

Правила:

- В слоте лежит `instanceId`, а не `itemId`.
- **Артефакты физически занимают слоты пояса и не лежат в инвентаре.** Их число ограничено `armor.artifactSlots + belt.artifactSlots`; без брони и пояса слотов ноль.
- Снятие рюкзака уменьшает `rows`: предметы, которым не хватило места, уходят в переполнение (раздел 9).
- Снятие брони или пояса уменьшает число слотов артефактов. Артефакты сверх нового лимита **перекладываются в инвентарь; если места не хватает всем — снятие блокируется** (пояс/броня остаются надетыми, артефакты на месте).
- **Число слотов артефактов не задаётся в коде:** оно суммируется из надетого, в сейве не хранится.
- Остальные надетые предметы (оружие, шлем, броня, рюкзак, пояс) остаются в `inventory.items` и занимают клетки — экипировка не освобождает сетку.
- **Прочность брони и шлема — в файле предмета** (`durabilityMax`, `material`, `durabilityFactor`, `quality`), у экземпляра хранится текущая `durability`. **При `durability = 0` предмет считается сломанным:** он остаётся в слоте, но не даёт защиты, не участвует в расчётах урона и износа и не может быть использован.
- **Формула износа:** `износ = ceil(урон / (durabilityFactor × quality × 10))`, но не меньше 1 за попадание; при нулевом уроне износа нет. Потеря прочности пропорциональна урону и падает с ростом прочности материала и качества; пулестойкость на износ не влияет (она уменьшает урон по здоровью). Материал: `light` 1.0, `medium` 1.2, `heavy` 1.5, `exoskeleton` 1.7; качество по умолчанию 1.

### 11.6. `Formula` — формула как данные

Требование: **формулу урона можно поменять в любой момент, не переписывая код, который её применяет.** Поэтому формула — строка в данных, а в коде живёт один универсальный вычислитель, который ничего не знает про конкретную формулу.

`Formula` (вид `formulas`):

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `id` | string | да | `formula_damage_base` |
| `expression` | string | одно из трёх | выражение на мини-языке (ниже) |
| `value` | number | одно из трёх | константа: то же самое, но числом |
| `table` | `[{ x, y }]` | одно из трёх | таблица: линейная интерполяция по `x` |
| `variables` | `[{ name, descriptionKey }]` | да | какие имена формула вправе использовать |
| `result` | enum | да | `int` или `float` |
| `clampMin` | number | нет | нижняя граница результата |
| `clampMax` | number | нет | верхняя граница результата |
| `descriptionKey` | string | нет | что считает формула |

**Одна формула — три представления, конвертируются без кода.** У записи ровно одно из полей `expression`, `value`, `table`:

- `expression` — полное правило;
- `value` — просто число (вырожденный случай: «формула» без счёта);
- `table` — набор точек с линейной интерполяцией (вырожденный случай: правило, заданное вручную).

Конвертация — правка того же файла: формулу свести к числу (`"value": 12`), число развернуть в таблицу, таблицу заменить выражением. Идентификатор и все ссылки на него не меняются, код не трогается. Валидатор принимает ровно одно из трёх полей и ругается, если заполнено два.

**Мини-язык выражений** — общий для всех формул:

- числа (целые и дробные, разделитель — точка), имена переменных из `variables` и констант из `Balance.constants`;
- операторы `+`, `-`, `*`, `/`, `%`, скобки, унарный минус;
- функции: `min`, `max`, `abs`, `floor`, `ceil`, `round`, `clamp(x, lo, hi)`.

Чего в языке нет намеренно: строк, индексов, свойств, доступа к объектам, вызовов, условий, циклов. Язык крошечный — его можно разобрать за один проход и им нельзя ничего сломать за пределами арифметики.

**Переменные и константы — разные вещи.** Переменная приходит из кода (урон, защита, уровень локации) — это контракт. Константа объявлена в данных (`Balance.constants`) и доступна всем формулам по имени. Порядок разрешения имени: `variables` → `constants`; имя, которого нет нигде, — ошибка загрузки.

**Число баланса — всегда имя, а не литерал в выражении.** Если подкручиваемый коэффициент встречается в нескольких формулах или его хочется менять отдельно, он выносится в `Balance.constants`: `0.15` в формуле заменяется на `rarity_curve`, и правка одной константы меняет все формулы сразу. Литерал в выражении допустим только для структурных чисел (0, 1, 2), а не для баланса.

**Правила:**

- Выражение разбирается **один раз при загрузке данных** в дерево; в бою дерево только вычисляется, строка заново не парсится.
- Синтаксическая ошибка, неизвестное имя переменной или неизвестная функция — **ошибка загрузки источника**, а не тихий ноль в бою.
- Деление на ноль даёт `0` и пишет предупреждение: бой не должен падать из-за данных.
- `result = int` — округление к ближайшему, затем `clampMin`/`clampMax`. Если границы не заданы, действуют значения по умолчанию из `CombatSettings`.
- Формулу можно переопределить модом по `id` — обычное правило замены записи (раздел 3.5).
- Формула меняется правкой JSON; в редакторе — перезагрузкой данных, в сборке — правкой файла в `Mods/`. Пересборка не нужна, пока меняется выражение, а не набор переменных.

**Контракт переменных.** Имена переменных — это интерфейс между кодом и формулой. Код передаёт значения по этим именам, формула решает, как их сложить. Добавление новой переменной — правка кода, изменение комбинации — только правка JSON.

| Формула урона: переменная | Что означает |
| --- | --- |
| `damage` | базовый урон после множителей скилла и патронов |
| `penetration` | суммарная бронебойность (оружие + патрон) |
| `protection` | защита цели по типу урона этого удара |
| `distance` | дистанция в зонах (0 — вплотную … 3 — далеко); нужна позиционным скиллам вроде «Тарана» |

Текущая формула урона (`formula_damage_base`):

```
max(0, damage - max(0, protection - penetration))
```

**Другие формулы (все правила, где есть счёт, — выражение):**

| Формула | Переменные | Зачем |
| --- | --- | --- |
| `formula_ambush_chance` | `danger`, `playerLevel`, `tier`, `timeOfDay`, `weather` | шанс, что первым ходит враг; факторы открыты |
| `formula_spawn_weight` | `baseWeight`, `danger`, `tier` | вес объекта при генерации локации |
| `formula_spawn_chance` | `baseChance`, `tier` | шанс появления локации по редкости |
| `formula_rarity_weight` | `baseWeight`, `rarityOrder`, `locationTier`, `danger`, `enemyTier`, `playerLevel` | вес редкости при выпадении: чем выше тир локации и врага, тем вероятнее редкое |
| `formula_route_length` | `danger`, `tier`, `locationTier` | сколько отрезков пути до точки интереса |
| `formula_travel_cost` | `baseStamina`, `baseHours`, `length`, `danger` | стоимость перехода: выносливость и часы |
| `formula_price` | `base`, `reputation`, `traderModifier` | цена с репутацией (раздел 4.9) |

Правило: если правило содержит арифметику и его захочется подкрутить, оно становится `Formula`, а не полем с коэффициентом. Список переменных каждой формулы фиксируется в её `variables`; код передаёт значения по этим именам.

### 11.7. `CombatSettings`

Единственная запись вида `combat`: какие формулы использовать.

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `id` | string | да | всегда `combat` |
| `damageFormulaId` | string | да | формула урона; по умолчанию `formula_damage_base` |
| `healFormulaId` | string | нет | формула лечения ❓ если понадобится |
| `clampMin` | number | нет | нижняя граница результата по умолчанию |
| `clampMax` | number | нет | верхняя граница результата по умолчанию |
| `apRestore` | enum | да | `full` — полностью каждый ход (принято); `partial` — по `apPerTurn`; `none` — только запас на бой |
| `apPerTurn` | int | нет | сколько ОД восстанавливается при `apRestore = partial` ⏸ |
| `initiative` | enum | да | `playerFirst` — игрок всегда первый; `formula` — порядок считает `initiativeFormulaId` (принято) |
| `initiativeFormulaId` | string | нет | формула засады; обязательна при `initiative = formula` |
| `zoneShiftFree` | int | да | сколько зон можно пройти бесплатно за ход (принято: 1) |
| `zoneShiftApCost` | number | нет | цена сдвига сверх бесплатного, в ОД ⏸ |
| `attackApCost` | int | нет | цена атаки в ОД; по умолчанию 1 |
| `reloadApCost` | int | нет | цена перезарядки в ОД; по умолчанию 1 |
| `accuracyClose` | number | нет | множитель меткости вплотную/близко; по умолчанию 1.4 |
| `accuracyMid` | number | нет | множитель меткости на средней дистанции; по умолчанию 1.0 |
| `accuracyFar` | number | нет | множитель меткости на дальней дистанции; по умолчанию 0.8 |

Правила:

- `CombatSettings` не содержит чисел баланса — только ссылки на формулы, режимы и границы, чтобы смена правила была правкой одного поля.
- При `initiative = formula` шанс засады считает `formula_ambush_chance` от факторов (сложность локации, уровень игрока, тир, время суток, погода); список переменных открыт. Как именно засада применяется (один бросок на бой, на ход или на противника) — открытый вопрос реализации (манифест §13).
- Зоны дистанции — те же, что у `Skill.range` (`melee`, `close`, `mid`, `far`), отдельных настроек не требуют.
- Сдвиг по зонам: `zoneShiftFree` зон за ход бесплатно, дальше — по `zoneShiftApCost`. Это правило боя, а не структура: меняется здесь, в данных.

### 11.8. `BalanceSettings` (вид `balance`)

Единственная запись `balance` — именованные числа баланса, на которые ссылаются формулы.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | всегда `balance` |
| `constants` | `{ [name]: number }` | константы по имени: `{ "rarity_curve": 0.15, "durability_per_shot": 0.5 }` |
| `statRounding` | enum | `round`, `floor`, `ceil` — как округлять раскатанные характеристики; цены округляются по `EconomySettings` |

Правила:

- **Три уровня чисел.** Числа контента (урон конкретного автомата, цена патрона) живут прямо в записи `Item` — это данные предмета. Числа правил (шанс, кривая, множитель) живут в `Formula`. Коэффициенты, общие для нескольких формул, — в `constants`.
- Константа — просто число; она не может ссылаться на формулу, циклов нет. Переопределяется модом как обычная запись `balance` (раздел 3.5), но осторожно: она общая.
- Константу можно «развернуть» обратно в формулу или в таблицу, не меняя код: ссылки идут по имени, а представление — дело данных.
- Валидатор: каждая константа, использованная в формуле, существует; неиспользованная константа — предупреждение; имена — `snake_case`, без пробелов.
- Балансные правки — это правка `balance.json` или выражения формулы; пересборка не нужна, в редакторе — перезагрузка данных.

Пример:

```json
{
  "id": "balance",
  "statRounding": "round",
  "constants": {
    "damage_floor": 0,
    "durability_per_shot": 0.5,
    "rarity_curve": 0.15,
    "ambush_base": 0.2,
    "ambush_danger": 0.3,
    "ambush_tier_step": 0.1,
    "ambush_cap": 0.9
  }
}
```

Формула засады с константами вместо литералов:

```
clamp(ambush_base + danger * ambush_danger + max(0, tier - playerLevel) * ambush_tier_step, 0, ambush_cap)
```

Поменяв `ambush_danger` в `balance.json`, вы меняете поведение всех боёв — код не трогается. Если формула стала не нужна, её `expression` заменяется на `"value": 0`, и поведение становится фиксированным без правки кода.

## 12. Актёры: базовая сущность и наследники

Все персонажи мира — одна сущность `Actor` с полем-дискриминатором `type`. В JSON наследования нет: общие поля лежат в базе, частные — в блоке наследника, `type` говорит загрузчику, какой блок читать.

```
Actor                      (общие поля, раздел 12.1)
├── Npc        type=npc    неагрессивный персонаж (12.3)
│   └── Trader type=trader торговец, наследник NPC (12.4)
└── Enemy      type=enemy  агрессивный (12.5)
```

Один вид данных (`kind = "actors"`), один id-список, три файла по смыслу. Ссылки между сущностями всегда идут через `actorId`, а допустимый `type` проверяет валидатор.

### 12.1. `Actor` — базовые поля

| Поле | Тип | Обязательное | Смысл |
| --- | --- | --- | --- |
| `id` | string | да | `npc_caravan_boss`, `trd_hub_smuggler`, `enemy_dog` |
| `type` | enum | да | `npc`, `trader`, `enemy` |
| `nameKey` | string | да | ключ локализации имени |
| `descriptionKey` | string | нет | ключ локализации описания |
| `portrait` | string | нет | путь к портрету |
| `factionId` | string? | нет | чей; `null` — одиночка или дикий |
| `locationId` | string? | нет | где стоит в мире; `null` у тех, кто появляется через `SpawnEntry` |
| `tags` | string[] | нет | свободные метки |
| `combat` | CombatBlock? | нет | боевые характеристики; **обязателен** для `enemy` |

### 12.2. `CombatBlock`

| Поле | Тип | Смысл |
| --- | --- | --- |
| `tier` | int | тир |
| `health` | int | запас здоровья |
| `ap` | int | очки действия |
| `protection` | object | `{ [damageTypeId]: number }` — защита по типам урона |
| `skills` | string[] | какие скиллы применяет |
| `ammo` | object? | `{ magazineSize: int, reserve: int, caliber?: string }` — запас патронов врага |
| `level` | int | уровень актёра; по умолчанию 1 |
| `accuracy` | number | базовая меткость актёра 0..1; по умолчанию 0.8 |
| `accuracyBonus` | number | бонус меткости от талантов; по умолчанию 0 |
| `ai` | enum | `aggressive`, `cautious`, `ranged`, `passive` ❓ набор |

Правила:

- У `enemy` блок обязателен, у `npc`/`trader` — нет. Персонаж без `combat` в бой не вступает и не может быть целью атаки.
- **Враг живёт по общим правилам:** у него есть патроны, он тратит их на скиллы с `ammoCost > 0` и перезаряжается. Отличие от игрока — только механики выживания (еда, вода, сон) к нему не применяются.
- `ammo` обязателен, если хотя бы один скилл врага имеет `ammoCost > 0`; иначе поле можно не задавать.
- В бою магазин врага заполняется до `magazineSize`, патроны тратятся по `ammoCost`, перезарядка берёт из `reserve` и стоит ОД.

### 12.3. `Npc` (`type = npc`)

Наследник `Actor`, добавляет:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `roles` | string[] | `questGiver`, `dialogue`, `informant` |
| `quests` | string[] | какие квесты выдаёт |
| `dialogueId` | string? | ссылка на `Dialog` (раздел 15.4); нет — персонаж молчит |

Правило: **неагрессивный по умолчанию.** `Npc` не начинает бой сам; если `combat` задан, `ai` должен быть `passive` или `cautious`. Агрессивное поведение по умолчанию — только у `enemy`.

**Враждебность — состояние, а не тип.** Неагрессивный персонаж может стать врагом: по сценарию квеста, из-за репутации (ниже порога — враждебна фракция целиком) или из-за удара игрока: первый удар делает NPC врагом и снижает репутацию его фракции, свидетели тоже враждебны. `type` при этом остаётся `npc`; текущее состояние хранится в сейве (`WorldState.actorStates`, раздел 17), потому что это изменяемое значение, а не описание.

### 12.4. `Trader` (`type = trader`)

Наследник `Npc`: те же поля плюс торговля.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `assortment` | `[{ itemId, stock, restock }]` | что продаёт |
| `playerBuyModifier` | number | множитель цены, по которой **игрок покупает** у торговца |
| `playerSellModifier` | number | множитель цены, по которой **игрок продаёт** торговцу |
| `requirements` | Requirements | когда торговец доступен |

Правила:

- `type = trader` требует `assortment`; `roles` обязан содержать `trader`.
- Имя, портрет, локация и фракция — из базовых полей, не дублируются.
- ✅ РЕШЕНО: у торговцев **ограниченный запас с пополнением**. Поля `stock` и `restock` — данные; правило пополнения (период, объём) задаётся в `Trader` и `EconomySettings`, числа — `⏸`.

### 12.5. `Enemy` (`type = enemy`)

Наследник `Actor`: общие поля плюс боевые.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `combat` | CombatBlock | **обязателен** |
| `lootTable` | string? | что выпадает |

Правило: враг не знает, где он появился. Привязка к местности и уникальность экземпляра — свойства `SpawnEntry` (раздел 14.2), поэтому `locationId` у `enemy` обычно `null`.

### 12.6. `DamageType`

Файлы: `Assets/Data/damage/*.json`, коллекция `damage/col_damage.json`. Вид сущности — `damageTypes`.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | `dmg_bullet` |
| `nameKey` | string | «Пулевой» |
| `damageKind` | enum | `bullet`, `anomaly`, `physical`, `elemental` |
| `stackable` | bool | может ли тип складываться в один заход урона; по умолчанию `false` |

Правила:

- Типы урона — **данные**: `protection` у брони и шлема проверяется по загруженным `damageTypes`, неизвестный ключ — ошибка `error.unknown_damage_type`. Новый тип добавляется файлом, код не меняется.
- **Пулевой урон** — `dmg_bullet`: обычное оружие без особых свойств. От него защищает **пулестойкость** — `protection.dmg_bullet`.
- Аномалии наносят урон своих типов; **мутанты могут наносить те же типы**, что и аномалии. Поэтому защита не сводится к «броня от пуль».
- У оружия есть **бронебойность** (`armorPenetration`): она снижает защиту цели по типу урона этого оружия.
- Формула расчёта — **данные, а не код**: выражение живёт в `Formula` (раздел 11.6), имя используемой формулы задаёт `CombatSettings.damageFormulaId`, текущая — `formula_damage_base`. Числа и порядок модификаторов — на этап баланса; сама формула меняется без пересборки.

| --- | --- | --- |
| `hub` | мирная зона, начало маршрутов | база, лагерь |
| `route` | отрезок пути между точками интереса | участок трассы, коридор, поле, тоннель |
| `site` | точка интереса в конце пути | дом у дороги, лагерь, аномалия |
| `interior` | внутренность точки интереса | комната, подвал, второй этаж |

**Нарративная связность.** Игрок не должен «прыгать» из трассы в болото или в дом. Переход разрешён, только если совпадают роль, путь и теги: дорога продолжается дорогой, точка интереса достигается **после** отрезков пути, а внутрь дома ведёт дверь, а не сама трасса.

Правила:

- **`route` не переходит в `site` без пути.** Сначала маршрут из нескольких `route` (длина — `Topology.routeLength`, может считаться формулой), потом `site`.
- **`interior` не соединяется напрямую с `route` или `hub`.** Внутрь ведёт только `site` через дверь, лестницу или люк.
- **`hub` соединяется с `route`** (дорога, тропа) и с другими хабами (быстрый переход).
- **Один `via` на ребро:** ребро описывает ровно один способ перехода, смешивать «дорогу и дверь» нельзя.
- Каждый тег `via` требует тегов у локации (таблица в 14.1.1): `road` — только у дороги, `corridor` — только внутри.
- Наратив держится не только тегами: описание (`textKey`/`descriptionKey`) должно объяснять, как игрок сюда попал, но проверяется это человеком, а не валидатором.

### 14.1.1. `Connection` (ребро)

| Поле | Тип | Смысл |
| --- | --- | --- |
| `toId` | string | id `LocationTemplate` или `spawn_` шаблона ветки |
| `via` | enum | `road`, `path`, `door`, `gate`, `stairs`, `hatch`, `corridor`, `tunnel` |
| `length` | int? | сколько «шагов» занимает переход; для `route`-цепочек это длина отрезка ⏸ |
| `oneWay` | bool | переход только в одну сторону; по умолчанию `false` |
| `hidden` | bool | переход не виден без открытия (секрет, замаскированный вход) |
| `requirements` | Requirements? | что нужно, чтобы переход открылся |

**Таблица `via` → обязательные теги и допустимые роли:**

| `via` | Обязательные теги | Из роли | В роль |
| --- | --- | --- | --- |
| `road` | обе стороны: `road`, `outdoor` | `hub`, `route` | `hub`, `route`, `site` |
| `path` | обе стороны: `outdoor` | `hub`, `route`, `site` | `hub`, `route`, `site` |
| `door` | назначение: `indoor`; источник: `indoor` или `outdoor` | `site`, `interior` | `interior` |
| `gate` | обе стороны: `outdoor` | `site` | `site` |
| `stairs` | обе стороны: `indoor` | `site`, `interior` | `interior` |
| `hatch` | назначение: `indoor` или `underground`; источник: любой из этих | `site`, `interior` | `interior` |
| `corridor` | обе стороны: `indoor` | `interior` | `interior` |
| `tunnel` | обе стороны: `underground` | `route` | `route` |

Так «дом» (`indoor`, `nodeType = site`) не может стоять в конце трассы напрямую — к нему ведёт `path`, а внутрь — `door`. Болото (`water`) не соединяется дорогой: только тропой, и только если у обеих локаций есть `outdoor`.

### 14.1.2. Стоимость перехода

Переход стоит ресурсов: выносливости и времени мира. Стоимость — данные, а не константа в коде.

| Поле в `Connection` | Тип | Смысл |
| --- | --- | --- |
| `cost` | `{ stamina: int, hours: number }`? | переопределение стоимости ребра |

Правила:

- Базовая стоимость — по типу пути (`Topology.costs[via]`), например `road` дешевле `path`, а `tunnel` дороже обоих.
- Итог = `cost[via] × length`, если `length` задан; иначе просто `cost[via]`. Может считаться формулой `formula_travel_cost` (переменные `baseStamina`, `baseHours`, `length`, `danger`).
- `stamina` списывается с `player.stamina.current`, `hours` прибавляется к `world.time`.
- Если выносливости меньше стоимости, переход недоступен: кнопка неактивна, а не «переход в минус».
- Внутри одной локации (дверь, коридор) стоимость обычно нулевая: `cost = { stamina: 0, hours: 0 }`.
- Стоимость — данные: правка `topology.json` меняет цену всех дорог, правка одного ребра — только его.

### 14.5. `Topology` (вид `topology`, единственная запись)

Правила, из чего может состоять маршрут, чтобы мир был связным и логичным.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | всегда `topology` |
| `transitions` | Transition[] | разрешённые переходы «роль → роль через путь» |
| `routeLength` | `[int, int]` | сколько `route`-локаций между хабом и точкой интереса ⏸; база для формулы `formula_route_length` |
| `edgeLength` | `[int, int]` | вилка длины ребра: сколько «шагов» занимает переход, если `Connection.length` не задан; по умолчанию `[1, 2]` |
| `costs` | `{ [via]: { stamina: int, hours: number } }` | стоимость перехода по типу пути ⏸ |
| `hubFastTravel` | bool | можно ли ходить между хабами напрямую |
| `hubFastTravelCost` | `{ stamina: int, hours: number }`? | цена быстрого перехода между хабами |
| `maxBranchDepth` | int | предел вложенности веток от хаба ⏸ |
| `initialStamina` | int | стартовая и максимальная выносливость игрока; по умолчанию 10 |
| `dayStartHour` | number | час начала дня, по умолчанию 6 |
| `nightStartHour` | number | час начала ночи, по умолчанию 22 |

`Transition`: `{ from: nodeType, to: nodeType, via: string[] }`.

Пример:

```json
{
  "id": "topology",
  "transitions": [
    { "from": "hub", "to": "route", "via": ["road", "path"] },
    { "from": "route", "to": "route", "via": ["road", "path", "tunnel"] },
    { "from": "route", "to": "site", "via": ["path", "gate"] },
    { "from": "site", "to": "interior", "via": ["door", "stairs", "hatch"] },
    { "from": "interior", "to": "interior", "via": ["corridor", "door", "stairs"] },
    { "from": "hub", "to": "hub", "via": ["road", "path"] }
  ],
  "routeLength": [1, 3],
  "edgeLength": [1, 2],
  "costs": {
    "road": { "stamina": 2, "hours": 1 },
    "path": { "stamina": 3, "hours": 1.5 },
    "gate": { "stamina": 1, "hours": 0.5 },
    "tunnel": { "stamina": 4, "hours": 2 },
    "door": { "stamina": 0, "hours": 0 },
    "stairs": { "stamina": 0, "hours": 0 },
    "hatch": { "stamina": 0, "hours": 0 },
    "corridor": { "stamina": 0, "hours": 0 }
  },
  "hubFastTravel": true,
  "hubFastTravelCost": { "stamina": 5, "hours": 6 },
  "maxBranchDepth": 4,
  "initialStamina": 10,
  "dayStartHour": 6,
  "nightStartHour": 22
}
```

Правила:

- Переход разрешён, если для пары `(from.nodeType, to.nodeType)` есть `Transition`, а `via` входит в его список **и** в таблицу 14.1.1.
- Если переход запрещён, шаблон не загружается: ошибка на этап данных, а не «странная карта» в игре.
- `routeLength` задаёт, сколько отрезков пути проходить до точки интереса; значение может считаться формулой (раздел 11.6), поле — база.
- **Отрезки пути настраиваются:** глобальная вилка — `routeLength`, конкретная точка интереса может её переопределить через `LocationTemplate.approachLength`. Значение из формулы `formula_route_length` (переменные `danger`, `tier`, `locationTier`) имеет приоритет над базой.
- **Переход стоит ресурсов:** цена по типу пути — `Topology.costs`, переопределение — `Connection.cost`. Итог умножается на `length` ребра; списывается с `player.stamina`, время прибавляется к `world.time`. Не хватает выносливости — переход недоступен.
- **Маршрут строится на каждую точку интереса отдельно.** Для каждого `site` создаётся своя цепочка экземпляров `route`; разные локации не делят отрезки и рёбра. Число отрезков берётся из `approachLength` локации, иначе из `routeLength`; это независимый бросок на каждую локацию.
- **Длина ребра немного случайна.** Если `Connection.length` не задан, длина выбирается из `edgeLength`; стоимость считается как `cost[via] × length`. Авторское ребро с `length` фиксирует длину и не бросает её.
- `maxBranchDepth` ограничивает, насколько далеко от хаба может уйти ветка: защита от бесконечных цепочек.
- Генератор маршрута: `hub` → 1..`routeLength` отрезков `route` → `site`; `interior` прикрепляется к `site`. Промежуточные локации получают объекты и события по общим правилам.

| `kind` | enum | `story` — сюжетный, `repeatable` — повторяемый |

| `objective` | `targetId` указывает на |
| --- | --- |

- **Сюжетный квест (`story`) не проваливается.** Его можно только пройти; `consequences` у него — последствия событий, а не провала.
- **Повторяемый (`repeatable`) провалиться может** и бывает двух видов: `type = "life"` — один заход на жизнь: смерть игрока проваливает квест, после воскрешения и выхода из любого хаба начинается откат на `cooldownDays` игровых дней (срок зависит от сложности и награды); `type = "timed"` — ограничен сроком (`duration` во времени мира). Сданный повторяемый квест тоже уходит в откат.
- Провал и отказ от квеста теряют репутацию фракции (раздел 15.1, манифест §9).

### 15.4. `Dialog` (вид `dialogs`)

Диалог — отдельная сущность: набор узлов, у каждого — текст и варианты ответа.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | `dlg_caravan_boss` |
| `startNodeId` | string | с какого узла начинать |
| `nodes` | Node[] | узлы диалога; ≥ 1 |
| `requirements` | Requirements? | условия, при которых диалог вообще доступен |

`Node`: `{ id, speakerActorId?, requirements?, textKey, options: Option[] }` — кто говорит, что говорит, при каких условиях узел доступен, какие есть ответы.

`Option`: `{ id, textKey, requirements?, effects?, nextNodeId?, end? }` — что можно ответить, при каких условиях, что это меняет и куда ведёт. `end = true` закрывает диалог.

Правила:

- `nextNodeId` ссылается на узел того же диалога; циклы допустимы, тупиков быть не должно: у узла либо есть варианты, либо он закрывает диалог.
- **Условия входа проверяются на двух уровнях:** у диалога в целом и у узла. Диалог с невыполненными условиями не начинается; узел с невыполненными условиями недоступен в ветвлении.
- Условия — общий `Requirements` (раздел 13.3): репутация, квесты, открытия, предметы.
- Последствия варианта — общий `Effect` (раздел 11.3): выдать квест, изменить репутацию, включить враждебность, дать предмет.
- Недоступные варианты по умолчанию показываются неактивными; `hiddenIfUnavailable` скрывает их (`false` по умолчанию).

## 16. Крафт и ремонт: `Recipe`

| Поле | Тип | Смысл |

| `time` | `{ day, hours, phase }` | время мира: двигается при переходах и отдыхе |
| `weather` | string | текущая погода: `clear` / `rain` / `fog`; фаза суток — в `time.phase` (`day` / `night`) |
| `settings` | object | выбранные на старте настройки прохождения (`deathMode`, `lootLoss`) |
| `stash` | GridContainer? | склад в хабе ❓ |

Правила:

- `instanceId` уникален в пределах сейва.
- Если `itemId` из сейва исчез из данных, предмет не пропадает: помечается «неизвестный» и не ломает загрузку.
- `artifactSlots` в сейве **нет**: считается из надетого костюма и пояса.
- Формулы в сейве **не хранятся**: сейв содержит состояние, а не правила. Если понадобится зафиксировать версию формулы для старого сейва, в сейв добавляется `formulaVersion`, а не текст выражения.
- Враждебность персонажа — тоже состояние: она живёт в `actorStates`, а не в данных, потому что меняется по ходу игры.
- `settings` фиксируются при старте прохождения и не меняются задним числом; шаблоны значений — в `GameRules` (раздел 17.1).

### 17.1. `GameRules` (данные, вид `rules`)

Единственная запись: настройки прохождения, из которых игрок выбирает при новой игре.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | string | всегда `rules` |
| `deathMode` | enum | `hubReturn` — возврат в хаб с потерей лута (принято); `permadeath` — по смерти удаляется всё |
| `lootLossOptions` | `[{ id, titleKey, loss, share }]` | варианты потери лута: `loss` ∈ `none`, `partial`, `all`; `share` — доля теряемого для `partial` (0..1) ⏸ |
| `defaultLootLoss` | string | какой вариант выбран по умолчанию |
| `insuranceChance` | number | 0..1, шанс, что конкретная вещь не пропадёт при потере ⏸ |
| `insuranceAppliesTo` | enum | `loot` — только добыча вылазки; `all` — включая снаряжение |
| `baseRows` | int | строк сетки без рюкзака (принято 4) |
| `tierCount` | int | число тиров (принято 4, запас до 8–10) |

Правило: `GameRules` — данные, а не код; числа меняются без пересборки, а сейв хранит только выбор игрока.

## 18. Открытые вопросы по данным

1. **Цены:** конкретные `priceTiers` фракций, множители торговцев и правило округления на границах.
2. **Время и погода:** какие фазы, как считаются, что меняют кроме засады.
3. **Питание:** ставки расхода еды, воды и сна; что происходит при нуле и есть ли смерть от голода.
4. **Полный список типов урона** и какие типы наносят аномалии и мутанты (наполнение данных).
5. **Квесты «за жизнь»:** что ограничивает — число выполнений, смерть или тир.
6. **Диалоги:** структура узлов, условия вариантов, влияние на репутацию.
7. **Прочие формулы:** критический удар, лечение, сопротивление — какие нужны и с какими переменными.
8. **Ресурс перемещения:** как называется и как восстанавливается.
9. **Засада:** как применяется шанс — один бросок на бой, на ход или на противника; список факторов.
10. **Враждебность NPC:** атака игрока как повод, возврат отношений.
11. **Ремонт:** сколько прочности восстанавливает набор и станок, чем отличаются.
12. **Торговцы:** объём запаса и период пополнения.
13. **Склад в хабе:** нужен ли и какого размера.
14. **Android и WebGL:** когда и с какими ограничениями (сейчас целевая — Windows).
15. **Диапазоны `statRolls`** по шести ступеням — баланс; форма задана.

Закрыто и вынесено в схемы: стаки по `(itemId, durability)`, вес (отсутствует), ОД (полностью каждый ход), дистанция (зоны, один сдвиг бесплатно), износ (выстрел/попадание), ремонт (набор + станок), слоты артефактов (сумма), авторазмещение переполнения, модификаторы с убывающей отдачей, враждебность NPC (состояние в сейве), смерть (возврат в хаб, настраиваемая потеря, страховка), карта (хабы + радиальные вылазки), редкость и уникальность локаций, квесты (сюжетные не проваливаются; повторяемые двух видов), 4 тира, крафт только в хабах, торговцы с пополнением, все вычисления — формулы в данных, редкость только у оружия, брони и артефактов.

## 19. Правила валидации

**Структура**

- Все `id` уникальны внутри вида и внутри источника; совпадение между источниками — допустимое переопределение (раздел 3.5).
- `id` соответствует префиксу своего вида и шаблону `^[a-z][a-z0-9_]*$`.
- **Один файл — одна сущность:** нет массивов записей; `id` сущности совпадает с именем файла без `.json`.
- **Коллекция** — `collection: true`, обязательный `kind`, `entries` из файлов того же вида; дубли и циклы запрещены; коллекция не регистрируется как сущность.
- Сущность, не попавшая в коллекции и не указанная в каталоге напрямую, — предупреждение «недостижимый файл».
- `kind` файла совпадает с видом сущности; `abstract`-файл не попадает в реестр и не может быть целью ссылки.
- `extends` — ровно один родитель того же `kind`; цепочка без циклов; максимальная глубина — `maxExtendsDepth` ⏸.
- `include` — список существующих файлов, без циклов; порядок значим, следующий перекрывает предыдущий.
- После слияния `extends`/`include` сущность проходит все правила своего вида; `id`, `kind`, `schemaVersion` берутся из конечного файла.
- `schemaVersion` источника и файла не выше поддерживаемой игрой.
- Запись вида `economy` ровно одна; записей `combat`, `rules`, `balance`, `topology` тоже ровно одна.

**Моды**

- Корень мода — папка `Mods/<name>/`, внутри обязателен `mod.json`; без него папка игнорируется с предупреждением.
- `mod.json`: обязательны `schemaVersion`, `id`, `name`, `priority`; `id` мода уникален среди модов.
- `includes`, `entities`, `overrides.collections`, `overrides.entities` ссылаются на существующие файлы внутри папки мода (пути относительно корня мода).
- `overrides.entities` содержит файлы с `id`, которые уже существуют в базе или у ранее загруженного мода; иначе — предупреждение «перекрытие не найдено».
- `overrides.collections` содержит коллекции с `id`, существующим в базе; иначе — предупреждение.
- `removals` содержит существующие `id`; удаление `id`, на который ссылается неудалённый контент, — ошибка загрузки.
- Мод не содержит исполняемого кода и не может объявлять новые механики.
- Нарушение любого правила — мод не загружается целиком, остальные источники работают.

**Локализация**

- Каждый ключ из данных существует в `Strings.ru.resx`.
- Наборы ключей `ru` и `en` совпадают (расхождение — предупреждение, а не ошибка).
- Пустые значения запрещены.
- Формат ключа — `<вид>.<id>.<поле>`.

**Ссылки**

- `classId` → `WeaponClass`; `itemId` → `Item`; `lootTable` → `LootTable`; `templateId` → `LocationTemplate`; `spawnId` → `SpawnEntry`; `factionId` → `Faction`; `questId` → `Quest`; `statusId` → `StatusEffect`; `unlock_` id → `Unlock`; `damageTypeId` → `DamageType`.
- `actorId` → `Actor`; допустимый `type` зависит от поля: `giverActorId` — `npc` или `trader`, `actorId` у `SpawnEntry` и в сейве — `npc`, `trader` или `enemy`.
- `eventId` → `Event`.
- `dialogueId` → `Dialog`; `speakerActorId` → `Actor`.
- `rarity` и `rarityWeights[].rarityId` → `Rarity`; `features[]` → `Feature`; `skills[]` у экземпляра → `Skill`.
- `damageFormulaId` и `healFormulaId` → `Formula`.
- `initiativeFormulaId`, `formula_spawn_weight`, `formula_spawn_chance`, `formula_rarity_weight` → `Formula`.

**Предметы**

- `footprint` — положительные целые, каждое ≥ 1.
- `maxStack ≥ 1`; `count ≤ maxStack`.
- `tier ≥ 0` у всех предметов; у оружия и брони тир задаёт ступень силы.
- `Rarity.statRolls` содержит только известные ключи (`damage`, `accuracy`, `durabilityMax`, `protection`, `modifierValue`); диапазон `[min, max]` с `0 < min ≤ max`.
- `Rarity.order` уникален и идёт подряд 0..5; ровно шесть записей: обычная, редкая, особая, эпическая, легендарная, уникальная.
- `Rarity.skillPools[classId][]` → `Skill`, и каждый скилл входит в `classId.skills` — чужой класс-скилл запрещён.
- `Rarity.featurePool[]` → `Feature`; `skillRolls`/`featureRolls` не превосходят размер пула соответствующего класса.
- `Feature.categories[]` ⊆ `{weapon, armor, artifact}` и содержит категорию предмета, которому выпала особенность.
- `category = "weapon"` требует блок `weapon`; блок без соответствующей категории — ошибка.
- `accuracy` ∈ 0..1; `penetration ≥ 0`; `armorPenetration ≥ 0`; `damageModifier > 0`.
- `weapon.ammoCaliber` входит в `classId.ammoCalibers`.
- `weapon.skills` ⊆ `classId.skills`.
- Для `category = "ammo"` обязателен `caliber`; у каждого `weapon.ammoCaliber` есть хотя бы один патрон.
- `durabilityMax ≥ 1` у оружия, брони и любого предмета с износом.
- `durabilityPerShot ≥ 0` у оружия; у брони и шлема `durabilityFactor ≥ 0` и `quality > 0`, `material` — один из `light`, `medium`, `heavy`, `exoskeleton`.
- Ключи `protection` — существующие сущности `DamageType`; неизвестный ключ — ошибка `error.unknown_damage_type`; значения ≥ 0.
- `modifier.stat = "protection"` требует `damageTypeId`; при других `stat` поле не используется.
- `price.mode = "fixed"` требует `buy` и `sell`; `mode = "reputation"` требует `base` и `factionId`.
- `sell ≤ buy` для фиксированной цены.

**Инвентарь и состояние**

- Предмет не выходит за границы сетки: `x + w ≤ width`, `y + h ≤ rows`.
- Предметы не пересекаются по клеткам.
- `state = overflow` не содержит `x`/`y`; `state = placed` содержит их.
- `rotated = true` допустим только при `rotatable = true`; при повороте используется `[h, w]`.
- `rotatable = false` не запрещает `w == h`.
- `x, y ≥ 0`.
- `durability` присутствует тогда и только тогда, когда у предмета есть `durabilityMax`; `0 ≤ durability ≤ durabilityMax`.
- `durabilityMax` у экземпляра — раскатанное значение, а не копия `Item`: обязательно для оружия и брони, отсутствует у остальных.
- Ключи `stats` соответствуют `Rarity.statRolls`; значения лежат в диапазоне `base × [min, max]`.
- Стопка содержит только предметы с равными `itemId`, `durability` и `variantKey`; `maxStack = 1` запрещает стопку независимо от прочности.
- `durability` и `variantKey` у всех единиц стопки одинаковы; слияние с другой прочностью или другим вариантом не допускается.
- Количество надетых артефактов ≤ `armor.artifactSlots + belt.artifactSlots` (пустой слот даёт 0).
- `rarity` обязательна для `weapon`, `armor`, `artifact`; у остальных категорий (`consumable`, `ammo`, `trophy`, `material`, `quest`, `backpack`, `belt`) отсутствует.
- `skills` экземпляра ⊆ `Rarity.skillPools[classId]`, `features` ⊆ `Rarity.featurePool`, без повторов.
- `stats` для особенности хранится как `<featureId>.<stat>`, для артефакта — `modifier.<stat>`; имена не пересекаются.
- `variantKey` совпадает с пересчитанным по `rarity`+`skills`+`features`+`stats`; расхождение при загрузке — предупреждение, ключ не переписывается.
- Эффект `repair` адресуется предмету, а не актёру; `Recipe` с `kind = "repair"` обязан иметь `station` или требование предмета-набора.
- `Recipe` с `kind = "craft"` обязан иметь `station`: крафт только в хабах.
- Эффект `move` требует `zones ≠ 0`; итоговая дистанция не выходит за границы зон `melee`…`far`.
- Модификатор с `mode = "diminishing"` требует `falloff` в диапазоне 0..1.

**Актёры**

- `type` ∈ `npc`, `trader`, `enemy`; значение определяет, какой блок наследника обязателен.
- `type = enemy` требует `combat` и `ai` внутри него.
- `type = trader` требует `assortment` и `roles`, содержащий `trader`.
- `type = npc` не требует ни `combat`, ни `roles`.
- `type = npc` или `trader` с блоком `combat`: `ai` ∈ `passive`, `cautious`; `aggressive` и `ranged` у неагрессивных запрещены.
- `tier` внутри `combat` ≥ 0; `health > 0`; `ap ≥ 0`; ключи `protection` — существующие `DamageType`.
- `roles` у `trader` обязательно содержит `trader`; обратное верно: `roles` с `trader` только у `type = trader`.
- `lootTable` допустим только у `enemy`.
- `combat.ammo` обязателен, если хоть один скилл врага имеет `ammoCost > 0`; `magazineSize ≥ 1`, `reserve ≥ 0`.
- `factionId` и `locationId`, если заданы, ссылаются на существующие `Faction` и `LocationTemplate`.
- У `trader` переименованы множители: `playerBuyModifier` (покупает игрок) и `playerSellModifier` (продаёт игрок), `0 < значение ≤ 10`.

**Формулы**

- У записи `Formula` ровно одно из полей `expression`, `value`, `table`; два и больше — ошибка.
- `table` — не меньше двух точек, `x` строго возрастает; интерполяция линейная, значения за краями берутся с крайних точек.
- `expression` разбирается при загрузке; синтаксическая ошибка — отказ загрузки источника.
- Каждое имя в `expression` объявлено в `variables` **или** существует в `Balance.constants`; иначе — ошибка. Объявленная, но не использованная переменная — предупреждение.
- Допустимы только функции `min`, `max`, `abs`, `floor`, `ceil`, `round`, `clamp`; всё остальное — ошибка.
- `result` обязателен; `clampMin ≤ clampMax`, если заданы обе границы.
- `BalanceSettings` ровно одна; имена констант — `snake_case`; неиспользованная константа — предупреждение.
- `CombatSettings` ровно одна, `damageFormulaId` обязателен и разрешается в `Formula`.
- `CombatSettings.apRestore` ∈ `full`, `partial`, `none`; при `partial` обязателен `apPerTurn ≥ 1`.
- `CombatSettings.initiative` ∈ `playerFirst`, `formula`; при `formula` обязателен `initiativeFormulaId`.
- `zoneShiftFree ≥ 0`; `zoneShiftApCost ≥ 0`.
- Формула урона обязана объявлять как минимум `damage`; остальные переменные — по контракту раздела 11.6.

**Локации и квесты**

- `rarity` ∈ `common`, `uncommon`, `rare`, `unique`; `spawnChance` ∈ 0..1.
- `unique = true` требует `rarity = "unique"` и несовместим с `locationKind = "wild"` без квестовой привязки.
- Квестовые локации (`unique = true`) существуют в одном экземпляре на прохождение.
- `Quest.kind` ∈ `story`, `repeatable`; у `repeatable` обязателен блок `repeat`.
- `repeat.type = "life"` требует `cooldownDays ≥ 1`; `repeat.type = "timed"` требует `duration > 0`.
- `Quest.kind = "story"` не имеет `consequences` провала и не может быть провален.
- `locationKind` ∈ `hub`, `wild`, `special`; `nodeType` ∈ `hub`, `route`, `site`, `interior`.
- `objectCount`, `approachLength`, `edgeLength` и `routeLength` заданы парами `[min, max]` с `min ≥ 0` и `min ≤ max`; у `approachLength` и `edgeLength` минимум ≥ 1.
- `danger` и `spawnChance` ∈ 0..1; `unique = true` требует `rarity = "unique"`.
- `approachLength.max` не больше `Topology.maxBranchDepth`; если маршрут может быть длиннее одного отрезка, в топологии обязан существовать переход `route → route`.
- `Connection.toId` → `LocationTemplate`; переход `(from.nodeType, to.nodeType, via)` разрешён `Topology.transitions`; теги обеих сторон удовлетворяют таблице `via` (14.1.1); `hub → hub` возможен только при `Topology.hubFastTravel = true`.
- `Topology.costs` содержит цену для каждого `via`, встречающегося в `transitions`; стоимости неотрицательны; `initialStamina ≥ 0`, `0 ≤ dayStartHour < nightStartHour ≤ 24`.
- Для генерации нужны хотя бы один `hub` и хотя бы один `site`; иначе загрузка данных считается невалидной.
- `Stage.targetId` соответствует таблице «этап → тип цели» (раздел 15.2): `find`/`gather` → `Item`, `kill`/`talk` → `Actor` нужного типа, `visit` → `LocationTemplate`.
- `Dialog.startNodeId` ссылается на существующий узел того же диалога; все `nextNodeId` разрешаются внутри диалога.
- У каждого узла диалога либо есть варианты, либо он закрывает диалог; висячих узлов нет.
- `speakerActorId` → `Actor`; `dialogueId` у `Npc` → `Dialog`.
- `Event.requirements` и `Dialog.requirements`, если заданы, — валидный `Requirements`.

**Связность локаций**

- `LocationTemplate.nodeType` ∈ `hub`, `route`, `site`, `interior`.
- `connections[].toId` → `LocationTemplate`; `via` из перечня 14.1.1; `oneWay`, `hidden` — bool; `length ≥ 1`, если задано.
- Каждое ребро разрешено `Topology.transitions` для пары ролей и проходит таблицу `via` → теги.
- `interior` не имеет рёбер в `route` и `hub`; `hub` не имеет рёбер в `interior`.
- У `site` есть хотя бы одно входящее ребро из `route`.
- Каждая нехабовая локация достижима из какого-либо `hub`; висячих компонент нет.
- `routeLength[0] ≤ routeLength[1]`; цепочка `hub → route… → site` укладывается в эти границы.
- `approachLength[0] ≤ approachLength[1]`, если задано; иначе действует `Topology.routeLength` или `formula_route_length`.
- `Topology.costs[via]` задан для каждого `via`, который встречается в `transitions`; `stamina ≥ 0`, `hours ≥ 0`.
- `Connection.cost`, если задан, переопределяет `Topology.costs[via]`; отрицательных значений нет.
- `Topology` ровно одна; `hubFastTravel = false` запрещает прямые рёбра `hub → hub`.

**Правила прохождения**

- `GameRules` ровно одна; `deathMode` ∈ `hubReturn`, `permadeath`.
- `lootLossOptions[].loss` ∈ `none`, `partial`, `all`; у `partial` обязателен `share` ∈ 0..1; у `none` — `share = 0`; у `all` — `share = 1`.
- `defaultLootLoss` ссылается на существующий вариант.
- `insuranceChance` ∈ 0..1; при `permadeath` страховка не применяется.
- `baseRows ≥ 1`, `tierCount ≥ 1`.
- Сейв хранит выбранные `settings`, которые совпадают с одним из `lootLossOptions` и с `deathMode`.

**Генерация и контент**

- `minTier ≤ maxTier`, `objectCount[0] ≤ objectCount[1]`.
- `weight > 0` у спавна, лута и исходов.
- `rolls[0] ≤ rolls[1]`, `rolls[0] ≥ 1`.
- `choices` не пуст; все `effects` ссылаются на существующие id.
- `connections[].toId` ссылаются на существующие `LocationTemplate`, сами связи проверяются блоком «Связность локаций».

**Сейв**

- `instanceId` уникальны.
- Ссылка на удалённый из данных `itemId` не роняет загрузку, а помечается.
- `actorStates[].objectId` уникален в пределах сейва и ссылается на `SpawnedObject.objectId`; `actorId` разрешается в `Actor`.
- `player.stamina.current` ∈ 0..`player.stamina.max`, `stamina.max ≥ 0`.
- Строк сетки в сейве нет: `rows` вычисляется из `GameRules.baseRows` и рюкзака.
- `player.needs` — все шкалы 0..`max`; `max ≥ 1`.
- `world.time.hours` ∈ 0..24; `settings` соответствует `GameRules`.
- `schemaVersion` сейва выше поддерживаемой — отказ с сообщением, а не тихая потеря.

Результат: `damageTypeId`, `reloadTime`, `durabilityMax`, `durabilityPerShot` пришли из базы; `price` из базы заменён целиком (объект сливается глубоко, но `mode`, `base`, `factionId` перекрывают старые ключи); `sellable` и `droppable` — из миксина; `id` и `kind` — только из конечного файла.

### 20.19. Коллекция оружия

Файл-коллекция перечисляет всё оружие проекта; в каталоге указывается только она.

```json
{
  "schemaVersion": 1,
  "kind": "items",
  "collection": true,
  "id": "col_weapons",
  "entries": [
    "items/wpn_ak74.json",
    "items/wpn_akm.json",
    "items/wpn_mosin.json",
    "items/wpn_pm.json"
  ]
}
```

Коллекция может подключать другую коллекцию того же вида:

```json
{
  "schemaVersion": 1,
  "kind": "items",
  "collection": true,
  "id": "col_items_all",
  "entries": ["items/wpn_ak74.json"],
  "include": ["items/col_weapons.json", "items/col_ammo.json"]
}
```

Загрузчик при виде `collection: true` подтягивает каждый `entries` как сущность, а `include` разворачивает рекурсивно. Дубли `id` между коллекциями — ошибка: один файл должен быть объявлен ровно один раз.

### 20.20. Мод: манифест и перекрытие

```
Mods/hardcore_loot/
  mod.json
  Data/items/wpn_akm_tuned.json
  Data/items/col_weapons.json
  Localization/Strings.ru.resx
  Localization/Strings.en.resx
```

```json
{
  "schemaVersion": 1,
  "id": "hardcore_loot",
  "name": "Хардкорный лут",
  "version": "1.0.0",
  "author": "VlomInc",
  "priority": 10,
  "includes": ["Data/items/col_weapons.json"],
  "entities": ["Data/items/wpn_akm_tuned.json"],
  "overrides": {
    "collections": ["Data/items/col_weapons.json"],
    "entities": ["Data/items/wpn_ak74.json"]
  },
  "removals": ["itm_broken_trash"]
}
```

Коллекция мода с тем же `id`, что у базовой, заменяет список целиком — так добавляют новое оружие, не трогая базовый файл:

```json
{
  "schemaVersion": 1,
  "kind": "items",
  "collection": true,
  "id": "col_weapons",
  "entries": [
    "items/wpn_ak74.json",
    "items/wpn_akm.json",
    "items/wpn_akm_tuned.json"
  ]
}
```

Порядок: база загружается первой, затем моды по `priority`. Внутри мода сначала `includes` и `entities` (новые `id`), затем `overrides` — замена совпавших `id`. Мод с большим `priority` перекрывает мод с меньшим. Сломанный мод не загружается целиком и не мешает остальным.
